## 1. 设计裁定

| # | 裁定 | 理由 |
|---|---|---|
| J1 | **模式复制而非扩展 `ctx.goals`**：自建 `ctx.goalTree` 服务，沿用 DSH 的四态词汇/CAS revision/round cap/block reason 模式 | DSH goal "backed exclusively by the owning session log"= 单会话绑定；C1 要求跨重启、跨会话的权威状态源。且需求 3.1.1 的节点字段（完成标准/已确认事实/剩余预算/完成依据）远超 DSH GoalSnapshot |
| J2 | **权威源 = ctx.storage sqlite domain**；每次 accepted 变更**双写**一条 log-only session event（`goalTree/change`，全快照） | C1（机读状态权威）+ DSH 不变量 "Model-visible ⟺ logged"（目标状态若要进模型上下文必须可从 log 重建）。domain 为权威，log 为证据链与回放源 |
| J3 | **durable phase 四态与执行 stage 分离**（见 §2） | 需求 3.1.1 的"待规划→执行中→等待→验证中→完成/失败"与 DSH "active/paused/blocked/complete"是兩個正交问题：前者答"在干到哪一步"，后者答"还能不能继续"。混用会丢掉 blocked 的机器可路由 reason |
| J4 | 目标树与任务树分层：**目标**分解为目标（父子），**任务**是执行单元 DAG（T0.2） | 避免"目标即任务"的层次坍塌；目标完成标准（completionCriteria）由 T0.2 任务的后置验证汇聚满足 |
| J5 | 预算三维：round（DSH 词汇保留）+ token/时间/注意力配额（需求 3.2），父目标预算向子树分配 | 漂移管方向（T1.5）、预算管资源，互补不重叠 |

## 2. 状态模型

### 2.1 Durable phase（目标生命周期，四态）

沿用 DSH goal 语义，比较-and-set 推进：

```
create ──► active ──pause──► paused ──resume──► active
   │           │                                    
   │        block(code,msg)                  complete(outcome)
   │           ▼                                    
   │        blocked ──resume──► active            
   │           │                                    
   └──clear──► (tombstone) ◄── 任意非 complete 态可 clear
```

- `blocked` 是唯一 durable  stopped-by-problem 态，reason 携带稳定 lower-kebab code（路由用）+ message（人/模型读）；
- `complete` 是唯一成功终态，必填 `outcome`：`'success' | 'failed'`（失败也是完成的一种——DSH 无 failed 态，显式终态原则 C5 要求失败不可静默）；
- `clear` 保留 tombstone（GoalRef + clearedAt），历史不丢。

### 2.2 Execution stage（执行阶段，active 上的子状态）

| stage | 含义 | 进入条件 | 出口 |
|---|---|---|---|
| `planning` | 待规划：目标已立，完成标准未定或计划未批准 | create 默认 | 完成标准+首版计划就绪 → `executing` |
| `executing` | 执行中：任务分派进行中（T0.2 任务树有 in_progress） | 计划就绪 | 全部任务终态 → `verifying` |
| `waiting` | 等待：等人/等外部事件/等子目标 | 外部依赖未满足 | 依赖就绪 → 回 `executing` |
| `verifying` | 验证中：等待外部验证阀（完成标准回验） | 任务收敛 | 验证通过→complete；打回→`executing` |

- stage 仅存于 `active` phase；非 active 时 stage 保留最后值不参与路由；
- `waiting`/`verifying` 期间可 `pause`（长等待）——phase 与 stage 组合表达"暂停在等待中"。

### 2.3 与需求 3.1.1 的映射

| 需求词汇 | 落地 |
|---|---|
| 待规划 → 执行中 → 等待 → 验证中 → 完成/失败 | stage 序列（§2.2）+ phase complete(outcome) |
| 动态追加后继目标（排队） | 创建 sibling/child 目标带 `queuePosition`（§4.3） |
| 当前阶段 | phase + stage 组合 |

## 3. 数据模型

### 3.1 `GoalNode`（domain 记录，权威）

```ts type-equiv
/** 目标树节点全快照。每次 accepted 变更 revision+1。 */
interface GoalNode {
  readonly id: GoalId                 // branded，单调分配 goal-<n>
  readonly revision: number           // CAS：每次 durable 变更 +1
  readonly parentId?: GoalId          // 树边；根目标无
  readonly objective: string          // 人类请求的完成目标
  readonly completionCriteria: string[] // 可机读完成标准（T0.2 后置验证汇聚点）
  readonly phase: 'active' | 'paused' | 'blocked' | 'complete'
  readonly stage: 'planning' | 'executing' | 'waiting' | 'verifying'  // active 时有效
  readonly outcome?: 'success' | 'failed'  // phase=complete 时必填
  readonly blockedReason?: { code: string; message: string }  // phase=blocked 时必存
  readonly maxGoalRounds: number      // 本节点轮次预算总帽
  readonly roundsStarted: number      // 已准入轮数（ admitted round 才 +1）
  readonly budget: GoalBudget         // 资源预算（J5）
  readonly queuePosition?: number     // 排队序号（后继目标）
  readonly focus: boolean              // 是否当前焦点（每棵树恰有一个）
  readonly createdAt: number
  readonly updatedAt: number
}
```

```ts type-equiv
/** 资源预算三维 + 消耗账本指针。 */
interface GoalBudget {
  readonly tokens?: number             // token 总量帽
  readonly wallClockMs?: number        // 墙钟时长帽
  readonly attentionUnits?: number     // 人类注意力配额（审批次数/分钟数）
  readonly consumed: { tokens: number; wallClockMs: number; attentionUnits: number }
}
```

### 3.2 SQLite schema（`ctx.storage` sqlite domain，DomainSpec）

| 表 | 键 | 值 | 说明 |
|---|---|---|---|
| `goal_nodes` | GoalId | GoalNode 全快照 | 权威状态；layout `single`（记录小、整体读写） |
| `goal_history` | `GoalId#revision` | 变更记录 | 每次变更：操作、变更者（human/agent/coach）、diff 摘要、sessionEvent seq |
| `objective_edits` | 自增 seq | { goalId, from, to, reason, actor, at } | T1.5 目标持久性/一致性指标的数据面 |
| `calibrations` | 自增 seq | { goalId, driftType, action: 'restate'\|'echo'\|'reanchor'\|'nudge', detail, at } | T1.5 校准记录（外部验证阀兜底证据） |
| `constraint_snapshots` | GoalId | { pinned: string[], at } | C6：创建/编辑时的约束快照，约束保持率基线 |

- domain version=1；`invalidRecords` 默认（拒绝打开）——目标是权威数据，损坏必须响；
- `SCHEMA_VERSION` 单调递增（DSH 约定）。

## 4. 不变量与服务 API

### 4.1 树不变量（加载即校验，违反拒绝打开）

1. 无环：parentId 链必须终止于根；
2. 单焦点：每棵树（同一 root 祖先）恰一个 `focus: true`；
3. 预算守恒：子节点预算之和 ≤ 父节点剩余预算（分配时检查，消耗账本向上汇聚）；
4. CAS 严格：mutation 必须带期望 revision，不匹配拒绝（不静默重试）；
5. complete 必填 outcome；blocked 必填 reason；paused/blocked 不可再 block/pause。

### 4.2 `ctx.goalTree` 服务方法

```ts type-equiv
interface GoalTreeService {
  create(caller, req: CreateGoalRequest): GoalNode        // parentId 可选；默认继承父预算
  edit(id: GoalId, ref: GoalRef, req: EditGoalRequest): GoalNode
  focus(id: GoalId): GoalNode                            // 切换焦点（旧焦点 focus:false）
  pause | resume | block | complete | clear              // 语义同 DSH goal，均带 ref CAS
  recordRound(id: GoalId): GoalNode                      // admitted round +1，超帽拒绝
  consume(id: GoalId, usage: Partial<Consumed>): GoalNode // 预算记账
  get(id: GoalId): GoalNode | undefined
  tree(rootId?: GoalId): GoalNode[]                       //  detached 视图数组
  history(id: GoalId): readonly GoalChangeRecord[]
}
```

### 4.3 排队机制

后继目标 = `create({ parentId?, queuePosition })`。排队目标 `phase=active, stage=planning, focus=false`，不占用轮次；焦点切换即"开始处理下一个"。

## 5. 与 DSH 的对接点

| 对接面 | 机制 |
|---|---|
| 持久化 | `ctx.storage` sqlite domain（`defineDomain` + zod schema，`ctx.storage.domain.table('goal_nodes')`） |
| 模型可见性 | 每次 accepted 变更 append log-only session event `goalTree/change`（全快照 payload）；模型上下文经 system-prompt section（`goal:state`，order 紧随 `plan:policy`）或 `agent.inject()` 注入**当前焦点目标的裁剪视图**（objective/phase/stage/criteria/blockedReason/预算剩余） |
| 会话恢复 | boot 时 domain open + 树校验；session resume 后按 `focus` 目标恢复推进 |
| 轮次准入 | `recordRound` 与 DSH goal round 语义对齐：只有 admitted user-message turn 推进 roundsStarted |
| C6 联动 | `constraint_snapshots` 表的 pinned 约束是 T0.4 pinned 区的数据源之一 |

## 6. 验收标准（对 Gate G0 的贡献项）

1. **G0-②**：kill -9 进程后重启，目标树/焦点/预算/约束快照完整恢复，revision 不错乱；
2. **G0-①**：一个真实目标从 create 到 complete(success/failed) 全 phase×stage 组合可走通，blocked reason 可路由；
3. CAS 并发：两个并发 mutation 带同一旧 revision，恰好一个成功；
4. 树不变量 5 条各有拒绝用例（含注入式非法 parentId）；
5. 目标状态出现在模型上下文中，且可从 session log 重建（model-visible⟺logged 自检）。

### 验收结果回填（IT1 实现，2026-09-24，tda-goal-state 插件）

CI 四门全绿（类型门 6 包 / 不变量门 4 包 / 双写对账门 3 包 / 冒烟门 4 包；tda-goal-state 自身：不变量 14 例 + 双写 4 例 + 冒烟 3 例）。逐项对照：

1. **G0-②**：冒烟门 idle-kill 场景——kill -9 后重启，goal_nodes/goal_history/objective_edits/constraint_snapshots 五表状态原样、focus/revision/预算/约束快照完整；log↔domain 配对零差异 + replay-equivalence 等值 + 两级不变量复验过。
2. **G0-①**：冒烟门"phase×stage 全走通"例——真实目标 create → edit(stage: executing/waiting/verifying) → consume → block → resume → complete(success) 全组合走通，blockedReason 可路由；"进程内装配"例同路径经插件真实出口再走一遍。
3. **CAS 并发**：不变量门"CAS 严格"例——两个并发 consume 带同一期望 revision，恰好一个成功、一个 STALE_REVISION（不静默重试），账本只进一份；进程内装配例附 STALE 拒载（expectedRevision: 0）。
4. **树不变量 5 条拒绝用例**：不变量门——树完整（注入悬挂父引用/父环拒）、单焦点（注入双焦点拒、服务路径维持恰一）、预算守恒（服务路径超父剩余即拒/注入子帽和超父帽加载期拒/收紧自帽不得低于既有子帽和）、迁移守卫（paused/blocked 不可再 pause/block、非 active 不可直接 complete）、终态不可变（complete 后 edit/consume/clear 拒、clear 后一切变更拒）；另含 schema 恒等律两例（phase=complete 缺 outcome 打开即拒、paused 携 blockedReason put 即拒）。
5. **model-visible⟺logged**：冒烟门"phase×stage 全走通 + model-visible⟺logged 自检"例——focusView 渲染的 goal:state section 与 session log 事件逐一对应（进上下文的即可从日志重建）。

实现侧规格签名的必要超集（服务文件头明示）：所有 mutation 带 GoalRef（expectedRevision，不变量 4"CAS 严格"要求）与 actor（goal_history"变更者"列必要）。
