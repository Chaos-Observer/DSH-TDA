# T4.1 · 任务执行环 v1 规格（tda-executor 插件）

> 上游：《需求描述》v2.1 §3.3.3（coach/athlete 双环）、§3.2.1（任务树状态机）、§3.2.3（执行预算与硬约束 C5）、《T0.2》（任务池 CAS/预算三区/run 模型）、《T0.5》（派发执行通道）、《T2.5》（工作流执行器/合同层）、《T3.2》（审批与 ResumeTicket）、《T0.7》（审计/回放）、《实现施工方案》§3.6（daemon 宿主）+ 全局纪律 3（模型工具面零新增）。
> 定位：P4 产品化第一份规格，补"自动任务执行"缺口（2026-10-13 缺口对账：执行方不存在——daemon tick 只开窗+pump，`dispatch.execute`/`workflow.start` 均无自动调用方）。
> 本规格是施工依据；实现后回填验收结果。

## 1. 设计裁定

| # | 裁定 | 理由 |
|---|---|---|
| J1 | **定位=athlete 执行进程（双环之执行环），零新权威**：自建 `ctx.executor` 服务；任务状态权威永在 T0.2 `taskPool`（C1），执行环只是"把 ready 任务驱动到 complete 的策略与协议层"，一切状态变更经既有服务面 CAS | §3.3.3 双环结构中 coach（T2.1，已落环外观察）的对偶项缺失；执行环若自持任务副权威=第二真相源，违背 C1 与"监督服务只发票不代跑"同款的防总编排器原则 |
| J2 | **tick 驱动，不新起定时器**：执行环作为 `runtime.tick()` 的一个阶段（承 T0.2 J8 单 tick 语义：due→startRun 之后）；事件唤醒快速路径 v1 不做（1s tick 已够），只订阅 `taskPool/change` 置脏供观测 | 常驻调度宿主已存在（daemon），再起第二 timer=两套调度语义；§3.6 daemon 可 kill 重启零状态丢失的保证不被稀释 |
| J3 | **路由三模式，确定性选择禁 LLM 猜**：① `workflow`——任务匹配已固化 def（T2.5 consolidated）→ `workflow.start(actor, defId, params, taskId)`；② `dispatch`——无匹配 def → `dispatch.execute({taskId, role:'sidekick'})`（T0.5 通道，brief 只从 task 记录构造）；③ `direct`——stage=verifying 且完成标准可机读的收尾型，本地执行检查 | 匹配规则=纯函数（task 字段 × def 集 × params），同输入同输出可回放；模式选择的随机性会让审计无法解释"为什么这么执行"（P1 纪律 #12：裁决随记录落盘） |
| J4 | **认领与 owner 纪律**：执行环以固定 scheduler 会话身份 `taskPool.claim`（owner=scheduler 会话）；派发/工作流子会话的 owner 归属与释放按 T0.5/T0.6 既有 `releaseIfOwned` 身份判定纪律，执行环不得释放别人的认领 | IT3 装配教训（owner 归还必须按身份判定）在执行环维度复现：执行环是"调度器开窗内认领"的常态持有者，误释放=执行窗口中途失去 owner |
| J5 | **完成前必过验证（执行面外部验证阀）**：`complete(success)` 的前置=① evidence 非空（至少一个 entryId/可机读依据）② workflow 模式 contract 后置断言全过（T2.5 J4 校验器）③ verifyMode='evidence+lead' 时 Lead 审查 verdict=approve。任一不过 → 不当 success | Voyager 铁律/T2.5 J4：执行面的成功不能由执行者自证；C5"违反硬约束产生显式终态，绝不静默继续"在完成口的落地 |
| J6 | **重试与失败显式终态**：验证不过 → 预算内自动单步重试（`attempts ≤ maxRetries+1`，v1 maxRetries=1，params 可配）；超帽或连续验证不过 → `taskPool.complete(failed, unfinished)`；`consecutiveFailures` 达 T0.2 既有阈值 → `block(agent, {code,message})` 带机器可路由原因码。禁静默重试 | §3.2.3：预算耗尽→明确终态+未完成清单；T0.2 已有失败计数与 block 通道，执行环复用不另立判据 |
| J7 | **审批挂起接续=ResumeTicket 消费方（审批单点收敛在 dispatch 层）**：执行中触发审批只经 **dispatch 层高风险闸**（T0.5 J9：建单即 `requested`）——执行环**不预检**（判据同源，避免任务级+派发级双审批）；attempt 转 `awaiting-approval` 并记录 `approvalId`+`orderId`；人类批准 supervision 请求后，装配层桥把票据转为 `dispatch.approve`（requested→approved），执行环凭 ResumeTicket 经 `resumeAttempt` 续跑（复用既有单 `driveOrder`；重试才建新单）；**无超时自动过、无票不前溜** | T3.2 J5“监督服务只发票不代跑”——恢复逻辑在调用方，而执行环正是被等待的调用方（v1 前该角色缺位）；IT14 装配期实测：执行环预检与 dispatch 闸判据同源会造成双审批，故单点收敛（见施工方案 IT14 收口补记） |
| J8 | **让位与预算口径复用**：主任务活跃期（`isMainActive()` seam，v1 保守近似）新选任务排队不取消在飞；预算三区判定复用 T0.2 `zoneOfCaps` 唯一实现（converge 只放行收尾型 attempt、exhausted 不选新任务） | T2.1 J9/T2.6 J10 同款"不侵蚀主任务"纪律；预算口径全域单一（T0.2 既定：zone 唯一实现 zoneOfCaps，跨插件共用） |
| J9 | **立第二十事件族 `executor/change`，attempt 为权威域记录**：attempt 记录"选了什么任务/路由到什么/第几试/为何终态"——调度决策不可由其他域重放重建，按 P1 纪律 #12（不可重算→权威）必须域+事件双写；同时执行环**零注入直通**（deps 类型级不含 context/surface 写权）、**零模型工具面**（规划面观察执行态走 task_pool 既有 `task_list`/`task_get`） | 全局纪律 3（模型工具面零新增默认）；§5.4 控制流/数据流分离——执行环的决策记录是审计事实而非模型可见面；与 T3.4"不立新族"的区别：security 是纯验证层零运行时，executor 是运行时编排者，其 attempt 是回放解释链的必需环节 |
| J10 | **可回放与孤儿显式终态**：attempt 每次变更双写 `executor/change`（全快照）；重启时以 `bootAt` 为界收口在飞 attempt（承 T0.5 在途≠孤儿纪律）：早于本次启动的 `executing` attempt 显式终态（failed+unfinished）或经 `reconcileOrphans` 协同后续跑 | T0.7 replay-equivalence 硬判据覆盖 P4 新族（sources 扩一族，同 P1/P2/P3 惯例）；kill -9 冒烟三场景扩展执行环在飞态 |
| J11 | **单工作者 + 并发帽**：P4 单进程单执行环实例（多 worker fencing 留 U1，承 R6）；同时处于 `executing` 的 attempt ≤ `maxParallel`（v1=2，params 可配），超限的任务留待下轮 | 防子代理洪峰挤占主任务（§3.2.3 预算纪律的执行侧）；与 T0.5 dispatch 并发帽（默认 3）分层：dispatch 帽管子代理在飞，executor 帽管任务级并行 |
| J12 | **目标联动只经既有投影**：执行环不直接调 `goalTree`；目标 stage 推进由 T0.2 既有联动面（`taskPool/change` → `projectGoalStage` 幂等纯投影）自动完成 | 防执行环成为第二目标写入口（T1.5 J1 同款"检测器零目标写权"在执行环的对应纪律） |

## 2. 状态模型

```
selected ──claim──► claimed ──route+drive──► executing ──结论落定──► verifying ──验证过──► completed
                         │                      │                          │
                         │                      ├─ 审批挂起 ──► awaiting-approval ── ResumeTicket ──► executing（续跑）
                         │                      │                                                  │ 无票/拒绝 ──► failed
                         └──────────────────────┴── 重试帽内 ──► executing（attempts+1）
                                                └── 超帽/预算耗尽 ──► failed（unfinished 必填）
                                                └── 连续失败达阈 ──► blocked（reason.code 机器可路由）
```

| 状态 | 含义 | 进入 |
|---|---|---|
| `selected` | 通过选取过滤（ready/预算/让位/并发帽），尚未认领 | `select()` |
| `claimed` | 已 `taskPool.claim`（owner=scheduler 会话） | 认领成功 |
| `executing` | 按 mode 驱动中（workflow run / dispatch 单 / direct 检查） | 路由后启动 |
| `awaiting-approval` | 执行中触发人类审批，挂起等票 | T3.2 请求建立 |
| `verifying` | 执行侧已出结论/run 终态，验证中 | 结论落定 |
| `completed` | 验证过 ∧ `taskPool.complete(success)` 已落 | 完成 |
| `failed` | 验证不过/超帽/拒绝/预算耗尽；`unfinished` 必填 | 显式终态 |
| `blocked` | `consecutiveFailures` 达阈，`block()` 带原因码 | 显式终态 |
| `cancelled` | 人类/Lead 取消（`retry` 前的人工中止） | `cancel()` |

- attempt 是**任务级驱动记录**，与 T0.2 `task_runs`（执行窗口/周期概念）正交：一次性任务也有 attempt 但无 run 窗口；attempt 引用 `taskId`（+ 可选 `runIndex` 快照）。二者分工与合并评估见 U2。

## 3. 数据模型

### 3.1 `ExecutorAttempt`（domain 记录，权威）

```ts type-equiv
/** attempt 全快照。状态变更序列，CAS revision+1。 */
interface ExecutorAttempt {
  readonly id: AttemptId                 // branded，单调分配 exec-<n>
  readonly revision: number              // CAS
  readonly taskId: TaskId
  readonly goalId: GoalId                // 自 task 冗余快照（过滤/对账）
  readonly mode: 'workflow' | 'dispatch' | 'direct'
  readonly modeReason: string            // 路由依据（matched defId / no-def / verify-closeout）
  readonly defId?: string                // workflow 模式：匹配的固化定义
  readonly orderId?: DispatchId          // dispatch 模式：派发单（对账 T0.5）
  readonly runId?: string                // workflow 模式：run 挂靠（对账 T2.5）
  readonly status: 'selected' | 'claimed' | 'executing' | 'awaiting-approval'
                | 'verifying' | 'completed' | 'failed' | 'blocked' | 'cancelled'
  readonly attempts: number              // 第几试（1 起；重试+1）
  readonly ownerId: SessionId            // = scheduler 会话（J4）
  readonly verification?: VerificationReport
  readonly outcome?: 'success' | 'failed'
  readonly unfinished?: readonly string[]  // failed 必填（C5）
  readonly resumeTicketId?: string       // awaiting-approval 凭据（J7）
  readonly createdAt: number
  readonly settledAt?: number
}
```

```ts type-equiv
/** 验证报告（J5）。detail 为消毒摘要，禁原文。 */
interface VerificationReport {
  readonly kind: 'workflow-contract' | 'evidence-check' | 'lead-review'
  readonly passed: boolean
  readonly detail: string
  readonly evidenceEntryIds: readonly EntryId[]
}
```

### 3.2 `ExecutorParams`（策略行，权威）

```ts type-equiv
interface ExecutorParams {
  readonly revision: number
  readonly maxParallel: number           // executing 态 attempt 帽（v1=2）
  readonly maxRetries: number            // 单任务自动重试帽（v1=1）
  readonly selectionPolicy: 'priority-due'  // v1 唯一：priority 降序 → dueAt 升序 → createdAt 升序（承 T0.2 dispatch 序）
  readonly verifyMode: 'evidence' | 'evidence+lead'   // v1 默认 evidence
  readonly routerVersion: number         // 路由规则版本（回放解释，同 scorerVersion 范式）
}
```

### 3.3 SQLite schema（`ctx.storage` sqlite domain，DomainSpec）

| 表 | 键 | 值 | 说明 |
|---|---|---|---|
| `executor_attempts` | AttemptId | ExecutorAttempt 全快照 | 权威；layout `single` |
| `executor_params` | `'singleton'` | ExecutorParams | 策略权威；插件 Config 为默认种子 |

- domain version=1；`invalidRecords: 'reject'`（attempt 是审计事实，损坏即拒开）；
- 派生不建表：在飞集合（status∈{executing, awaiting-approval}）启动扫描重建；`bootAt` 由装配层注入（同 T0.5）；
- 事件族：`executor/change`（第二十族，内核 `events.ts` 登记；entityKind=`executor`，businessId=attemptId；params 行业务 id 恒 `params`）。未登记族双写即抛的内核门自动覆盖。

## 4. 不变量与服务 API

### 4.1 不变量（加载即校验 / 运行时强制）

1. **零直写权威**：deps 只注入 `taskPool/dispatch/workflow/supervision/goalLookup(只读)` 服务接口，类型级不含任何 domain 写权；执行环自身 domain 只有 `executor_attempts/executor_params`；
2. **路由确定性**：同 task 字段 + 同 def 集 + 同 params + 同 routerVersion ⇒ 同 mode 与 modeReason（纯函数 `route(task, defs, params)`，单测逐分支）；
3. **验证门**：无 evidence 非空 / contract 后置不过 / lead verdict≠approve ⇒ 禁 `complete(success)`；
4. **重试帽**：`attempts ≤ maxRetries+1`；超帽必落 failed+unfinished，禁第四次静默开跑；
5. **owner 纪律**：claim owner 恒为 scheduler 会话；执行环不释放非本 attempt 关联子会话的认领（`releaseIfOwned` 语义复用）；
6. **让位纪律**：`isMainActive()=true` 时不新选任务；在飞 attempt 不取消（让位只挡新不杀旧）；
7. **审批无自动过**：`awaiting-approval` 只能凭一次性 ResumeTicket 推进；过期/拒绝 ⇒ failed；
8. **孤儿显式终态**：`bootAt` 之前的在飞 attempt 重启后必达终态（failed+unfinished 或 reconcile 后续跑），禁僵尸；
9. **预算口径单一**：三区判定复用 T0.2 `zoneOfCaps`；converge 只放行收尾型（direct/verify 类），exhausted 不选新任务；
10. **零注入直通**：deps 不含 `ctx.context`/surface/injection 句柄；执行环的任何结论浮现只经 T0.5 ConclusionView + T1.1 gate 既有路；
11. **双写配对**：attempt 每次 accepted 变更 ↔ `executor/change` 事件逐一配对（内核对账门，第二十族；T0.7 J4 同款）。

### 4.2 `ctx.executor` 服务方法

```ts type-equiv
interface TaskExecutorService {
  initialize(): Promise<void>                        // 启动重建 + bootAt 孤儿收口（先于不变量注册，承 IT3 教训）
  select(now: number): readonly TaskSelection[]      // 纯函数：ready 集 → 过滤/排序后的选取序
  runOnce(now?: number): Promise<readonly AttemptReport[]>  // 单轮：选→认领→驱动→验证→收敛
  resumeAttempt(attemptId: AttemptId, ticket: ResumeTicket): Promise<ExecutorAttempt>  // J7 凭票续跑
  retry(actor: 'human' | 'lead', attemptId: AttemptId, ref: AttemptRef): ExecutorAttempt  // 手动重试（新 attempt 或 attempts+1）
  attempts(filter?: AttemptFilter): readonly ExecutorAttempt[]
  attempt(id: AttemptId): ExecutorAttempt | undefined
  inFlight(): readonly ExecutorAttempt[]             // executing + awaiting-approval
  params(): ExecutorParams
  setParams(actor: 'human' | 'lead', patch: Partial<Omit<ExecutorParams, 'revision'>>): Promise<ExecutorParams>
}
```

- **单轮执行序（runOnce）**：① `select(now)` 过滤（未认领 ∧ proposal 已批准 ∧ 预算区允许 ∧ 让位窗口允许 ∧ 并发帽内）→ 排序取前 N；② 逐任务 `claim` → 建 attempt（selected→claimed）→ `route()` → 按 mode 驱动至结论落定（verifying）；③ 验证（J5）→ 过：`taskPool.complete(success, evidence)` + attempt completed；不过：重试（帽内）或 `complete(failed, unfinished)` + attempt failed；④ 全部变更双写 + 返回报告；
- **driver 语义**：workflow 模式 `workflow.start` 后等 run 终态（T2.5 step 执行桥同步推进，本地 provider 下确定性）；dispatch 模式 `dispatch.execute`（T0.5 同步等结论）；direct 模式本地机读检查；
- **装配层桥（harness）**：`isMainActive()` seam（v1 保守近似：显式 activeRound 信号注入，默认 false）+ supervision 批准事件 → `resumeAttempt` 桥（同 T0.6 annotate 桥模式，零插件互 import）；
- **daemon 接线**：`runtime.tick()` 在执行既有 due/startRun/pump/drain 之后增加 `executor.runOnce()` 阶段；tick 报告扩字段 `{ executed, completed, failed, awaitingApproval }`；
- **无模型工具**：本插件不挂 `dsh-tda-tool-*` 工具集（全局纪律 3）。

### 4.3 模型可见工具集

无（见上）。执行态观测走 `dsh-tda-tool-task-pool` 既有 `task_list`/`task_get`（裁剪视图已含 phase/stage/zone/consumed/runCount/consecutiveFailures）。

## 5. 与 DSH 的对接点

| 对接面 | 机制 |
|---|---|
| 常驻宿主 | harness daemon `tick()` 新阶段（T0.2 J8 单 tick 语义；不新起 timer） |
| 派发执行 | `ctx.subagentDispatch.execute()` → DSH `ctx.subagents` spawn provider one-shot（T0.5 全套隔离契约，executor 不新增 DSH 依赖） |

## 6. 验收标准（对 Gate G4 的贡献项）

> Gate G4（建议随 P4 设立：任务驱动产品化闭环）= ① 需求进得来（T4.2 intake）② 任务自动转（本规格）③ 图谱问得出（T4.3）④ 人看得见（T4.4）。本规格承担②。

1. **端到端自动执行**：ready 任务被自动认领→路由→执行→验证→`complete(success)` 全链走通，全程无人工介入（scripted provider 确定性结论）；tick 报告 executed/completed 计数正确；
2. **路由三模式**：匹配 consolidated def → workflow 模式（run 挂靠 taskId，contract 前置不过不启动）；无 def → dispatch 模式（结论过 schema，evidence=conclusionEntryId）；verifying 收尾型 → direct 模式；路由纯函数同输入同输出（单测）；
3. **验证门**：结论缺 evidence / contract 后置不过 → 不当 success；自动重试一次；再不过 → `complete(failed, unfinished)` 且 unfinished 非空；
4. **审批接续**：high-risk 派发挂起 → attempt 转 awaiting-approval → 人类 token → `resumeAttempt` 续跑至 completed；拒绝/过期 → failed；无票前溜不可能（状态机单测）；
5. **重启恢复**：kill -9 于 executing/awaiting-approval 在飞态 → 重启后 bootAt 前 attempt 显式终态，无僵尸派发单（`reconcileOrphans` 协同），replay-equivalence 零违规；
6. **让位**：`isMainActive()=true` 期间不新选任务；信号撤销后自动续选；
7. **预算三区**：converge 区只放行收尾型 attempt、exhausted 不选新任务；`consume` 三维记账正确（对账 T0.5 settle 口径）；
