## 1. 设计裁定

| # | 裁定 | 理由 |
|---|---|---|
| J1 | **定位=需求对接阶段工程化，三阶段流水线**：`intake`（原始需求→结构化草稿）→ `clarify`（澄清循环，服务端生成问题）→ `confirm`（目标树提议+人类审批+代建）。产出=可执行目标树（T0.1），此后任务分解归 T4.5 规划器、执行归 T4.1 执行环 | 需求文档的生命周期始于"待规划"，但"如何到达一个形态良好的目标"从未工程化——现状只能手调 `goalTree.create` 服务 API。关注点分离：需求→目标→规划→任务→执行，本规格只做前两段 |
| J2 | **原文零进主上下文、零全文入域**：原始需求文本只作 T0.3 timeline chunk（`credential='user-original'`、`source='user'`）并经 T0.5 子代理 seam 抽取；domain 记录只存 `rawEntryId` 引用 + 结构化字段；主上下文只出现草稿摘要视图 | 同 T0.5 J5/T0.6 两层扫描纪律：长文本是上下文毒药；user-original 是最高凭证（§3.4.4 信任分层），但其**载体**必须是时间线 chunk 而非域内复制品 |
| J3 | **结构化抽取走子代理，问题生成走服务端**：草稿抽取=Sidekick 派发（outputSchema 白名单 `requirement-draft`，无指令字段）；澄清问题=`deriveQuestions(draft)` **纯函数**机械生成（按缺失字段模板），禁 LLM 产问题集 | 问题集质量决定需求质量，且提问面是注入面（"经提问诱导用户给出约束撤销类回答"）——服务端确定性生成可回放、可测试、无操纵空间；LLM 只负责"读懂原文填字段"这一数据流工序 |
| J4 | **目标树分解走 Lead，校验走确定性**：分解=Lead 角色派发（schema 白名单 `goal-tree-proposal`）；提交前必过 `validate()`——T0.1 树五不变量映射 + 完成标准非空 + tempId 引用完备 + 预算合法 + 根唯一。不过禁提请 | 外部验证阀在需求面的落地（Voyager 铁律同款：未校验零入库）；LLM 分解是建议，确定性校验是闸门——§5.4 控制流/数据流分离在需求面的对应形态 |
| J5 | **确认与澄清都走统一审批队列**：确认=`supervision.request(kind='requirement-confirm')`，v1 定级 medium（目标可 edit/clear 非不可逆；riskHint 可上调，服务端规则表兜底）；澄清轮=`kind='requirement-clarify'`（low）。commit 凭一次性 ResumeTicket；**无超时自动过** | T3.2 J1 单一 request() 入口纪律（七处上游收敛，不各造交互）；决策点⑤"高风险需审"在需求面的落点——建目标是后续一切执行的源头，须人在场 |
| J6 | **goalTree.create 由 intake 代建（v1 目标创建收敛入口）**：commit 按提议拓扑序（父先子后）逐节点 `goalTree.create(actor='agent', …)`；每个代建节点带 T0.1 扩展字段 `source='intake'` + `intakeProposalId`。**T0.1 domain version 2 扩展点**（两个可选字段，`compatibleVersions` 承 DSH 约定；同 P1 时 T0.1 补 `recordCalibration`/`objectiveEdits` seam 的先例） | 缺口对账第一项即"模型面无目标工具"——v1 不开模型工具（全局纪律 3），改以"服务端代建+审批"收敛创建入口，保证每个目标可溯源到需求提议；人类直接创建路径保留（走服务面，`source='human'`） |
| J7 | **需求变更=新草稿 supersede 链，禁改已确认提议**：confirmed 草稿被新草稿取代时只登记 `supersedes` 链指针；**已建目标不动**（目标权威归 T0.1，其编辑走 `goalTree.edit` 人类/Lead 路径） | intake 不持有目标编辑权——唯一代建时刻（J6）是经审批的结构性动作，此后一切目标变更加回 T0.1 既有 CAS 面；防 intake 长成影子目标权威 |
| J8 | **澄清轮次帽 + 超帽强制决断**：`clarificationRounds ≤ maxClarificationRounds`（v1=3，params 可配）；超帽带当前 openQuestions 全量提请人类一次性决断（escalation 呈现），禁无限澄清循环 | 防"澄清地狱"——人类注意力是一等预算（§3.2.1/§4）；无帽澄清=注意力滥用面（同 T3.2 J8 洪水帽思路） |
| J9 | **立第二十一事件族 `intake/change`，裁决随记录落盘**：draft/proposal 为权威域记录；LLM 抽取/分解的 `provider/model/schemaHash/at` 随草稿落盘（`ExtractionMeta`/`DecompositionMeta`）——回放可解释"这个草稿是谁用什么产生的" | P1 纪律 #12（裁决时参数随记录落盘）在需求面的落地；entityKind=`requirement`/`proposal`，businessId=draftId/proposalId；内核 events.ts 登记后双写门自动覆盖 |
| J10 | **v1 零模型工具面**：intake 服务入口=人类面/服务端（DSH 用户面或主会话显式调用服务）；模型主动发起（`intake_start` 等）留 U1 | 全局纪律 3（只有规格明文列了工具集的插件才挂工具）——本规格 v1 明文：无工具集；需求发起是低频高后果动作，人起人审比模型自起更符合决策点⑤ |
| J11 | **单活动草稿**：同一时刻至多一个 `status∈{drafting, ready, proposed}` 的草稿；新需求进来时旧草稿须先终态化（superseded/cancelled）。并行需求池留 U4 | 承 T0.1 单焦点语义（一次一个 current goal 的对偶）；多需求并行=多焦点=漂移面（T1.5 管方向，这里管入口） |
| J12 | **不碰任务层**：intake 只建目标树；任务分解/指派/执行归 T4.5/T4.1。接口以 `draftId`/`proposalId` 外键预留合流点 | 关注点分离的收尾条款；防 intake 长成总编排器（同 T3.2 J5"监督服务只发票不代跑"的防腐化原则） |

## 2. 状态模型

```
raw ──extract──► drafting ──(openQuestions 空)──► ready ──propose──► proposed ──approve+token──► committed
                     ▲                                │                    │
                     │                                │                    ├── reject ──► rejected
                     └── answer(澄清回答回写) ─────────┘                    └── cancel ──► cancelled
                     └── 超帽 escalation(带全量 openQuestions 提请决断)
committed ──(新草稿 supersede)──► superseded（链指针，已建目标不动）
```

| 状态 | 含义 | 进入 |
|---|---|---|
| `drafting` | 草稿已建，openQuestions 未清 | `intake()` / `answer()` 后仍有 blocking 问题 |
| `ready` | openQuestions 空（或无 blocking 项），可提请分解 | `deriveQuestions` 判定 |
| `proposed` | 目标树提议已生成待批 | `propose()` |
| `committed` | 已审批并代建目标树 | `commit()` |
| `rejected` | 人类驳回（带 reason） | `reject()` |
| `cancelled` | 人类/服务端取消（带 reason） | `cancel()` |
| `superseded` | 被更新草稿取代（链指针） | 新草稿 intake |

- draft 与 proposal 各有状态机；proposal 状态：`draft → pending-approval → approved → committed`（+ rejected/cancelled）；`confirmRequest()` 把 proposal 转 pending-approval 并建 T3.2 审批请求。

## 3. 数据模型

### 3.1 `RequirementDraft`（domain 记录，权威）

```ts type-equiv
/** 需求草稿全快照。CAS revision+1。 */
interface RequirementDraft {
  readonly id: DraftId                    // branded，单调分配 req-<n>
  readonly revision: number               // CAS
  readonly status: 'drafting' | 'ready' | 'proposed' | 'committed'
                | 'rejected' | 'cancelled' | 'superseded'
  readonly rawEntryId: EntryId            // 原文 timeline chunk（user-original）；域内禁存全文（不变量 1）
  readonly objective: string              // 一句话目标陈述
  readonly completionCriteria: readonly string[]   // ≥1 方可 ready
  readonly constraints: readonly string[]          // 硬约束候选（C5；确认后进 goal pinned）
  readonly budgetHint?: GoalBudgetCaps             // 初始预算帽（提议可细化）
  readonly openQuestions: readonly OpenQuestion[]
  readonly clarificationRounds: number             // 帽内（J8）
  readonly extraction: ExtractionMeta              // J9：provider/model/schemaHash/at
  readonly supersedes?: DraftId                    // 需求变更链
  readonly proposalId?: ProposalId
  readonly createdAt: number
  readonly updatedAt: number
  readonly settledAt?: number
}
```

```ts type-equiv
/** 澄清问题：服务端纯函数生成，无 provider 来源字段（不变量 2，类型级保证）。 */
interface OpenQuestion {
  readonly id: string                     // q-<n>（草稿内稳定）
  readonly field: 'objective' | 'completionCriteria' | 'constraints' | 'budget' | 'scope'
  readonly question: string               // 确定性模板生成
  readonly blocking: boolean              // true=不答不可 ready
  readonly answer?: string                // 截断存储（≤2000 字符，超长引用新 chunk）
  readonly answeredAt?: number
}
/** LLM 工序元数据（随记录落盘，回放可解释）。 */
interface ExtractionMeta {
  readonly provider: string
  readonly model: string
  readonly schemaHash: string             // requirement-draft schema 哈希
  readonly at: number
}
```

## 4. 不变量与服务 API

### 4.1 不变量（加载即校验 / 运行时强制）

1. **原文隔离**：draft/proposal 域记录禁存原始需求全文（只存 `rawEntryId`）；answer 超 `maxAnswerChars` 截断+引用；
2. **问题确定性**：`openQuestions` 只能由服务端 `deriveQuestions(draft)` 生成（纯函数同输入同输出）；`OpenQuestion` 类型无 provider 来源字段（类型级保证）；
3. **分解校验门**：proposal 状态离开 `draft` 前 `validation.passed=true`；检查项含 T0.1 树五不变量映射（无环/父存在/预算分配/焦点唯一/cleared 不复活）、criteria 非空、tempId 引用完备、根唯一；
4. **审批门**：commit 必经 `kind='requirement-confirm'` 批准 + 一次性 ResumeTicket；rejected/cancelled/过期禁建；
5. **创建收敛**：intake 代建的每个 goal 节点必带 `source='intake'` ∧ `intakeProposalId`（T0.1 v2 加载期断言对偶）；
6. **supersede 链**：草稿 supersede 只登记链指针；intake 无任何目标编辑/删除路径（deps 类型级只注入 `goalTree.create` 一个写方法 + 只读面）；
7. **零注入直通**：`requirement-draft`/`goal-tree-proposal` schema 白名单无任务指令类字段（无 taskId/status/owner/complete——同 T0.5 J4）；
8. **双写配对**：draft/proposal accepted 变更 ↔ `intake/change` 逐一配对（内核对账门）；
9. **轮次帽**：`clarificationRounds ≤ maxClarificationRounds`；超帽必 escalation（带全量 openQuestions 的决断请求），禁静默继续；
10. **单活动草稿**：`status∈{drafting, ready, proposed}` 的草稿至多一个；
11. **拓扑序**：`proposal.nodes` 父先子后；commit 依序创建，中途失败已建节点保留+attempt 显式终态（禁静默回滚半棵树）。

### 4.2 `ctx.intake` 服务方法

```ts type-equiv
interface IntakeService {
  initialize(): Promise<void>                                    // 启动重建 + 孤儿收口（先于不变量注册）
  intake(actor: IntakeActor, raw: { text: string; entryId?: EntryId }): Promise<RequirementDraft>  // 登记原文 chunk + 建草稿（J2）
  extract(draftId: DraftId): Promise<RequirementDraft>           // Sidekick 派发抽取（装配层桥 dispatch.execute；J3）
  deriveQuestions(draftId: DraftId): readonly OpenQuestion[]     // 纯函数（不变量 2）
  answer(actor: IntakeActor, draftId: DraftId, ref: DraftRef, answers: readonly { questionId: string; answer: string }[]): Promise<RequirementDraft>
  propose(draftId: DraftId): Promise<GoalTreeProposal>           // Lead 分解 + validate（J4）
  confirmRequest(actor: IntakeActor, proposalId: ProposalId): Promise<{ approvalId: string }>  // 建 T3.2 请求（J5）
  commit(proposalId: ProposalId, token: string): Promise<readonly GoalId[]>   // 凭票代建（J6）
  reject(proposalId: ProposalId, token: string, reason: string): Promise<GoalTreeProposal>
  drafts(filter?: DraftFilter): readonly RequirementDraft[]
  draft(id: DraftId): RequirementDraft | undefined
  proposals(): readonly GoalTreeProposal[]
  proposal(id: ProposalId): GoalTreeProposal | undefined
  params(): IntakeParams
  setParams(actor: 'human' | 'lead', patch: Partial<Omit<IntakeParams, 'revision'>>): Promise<IntakeParams>
}
```

- **装配层桥（harness，零插件互 import）**：`extract`/`propose` 的 LLM 工序经 dispatch 服务面执行（`dispatch.execute({taskId?, role})`——注意 intake 阶段**尚无 taskId**，v1 裁定：intake 的 LLM 工序走 dispatch 的**任务外通道**：装配层提供一个轻量 `intakeLlm` seam（内部仍用 subagents provider one-shot，复用 T0.5 隔离契约，但 brief 由 intake 构造、不经 task 记录）。若 DSH 工具层后续支持无任务派发，收敛为同一通道（U6 同款评估）；
- **ResumeTicket 接续**：approve → T3.2 产出 ResumeTicket → 装配层桥调 `commit(proposalId, ticket)`（同 T4.1 J7 桥模式）；
- **主上下文呈现**：`IntakeView = { draftId, status, objective, criteriaCount, openQuestionsCount, clarificationRounds }`（摘要；零原文）。

## 5. 与 DSH 的对接点

| 对接面 | 机制 |
|---|---|
| 审批交互 | `ctx.supervision.request/approve` → DSH User Approval / `user-questions` seam（T3.2 模式复制；T3.2 domain v2 扩展两种 kind，§3.4） |
| LLM 工序 | intake 专属 seam（内部=DSH `ctx.subagents` spawn one-shot，复用 T0.5 隔离契约：fresh child/outputSchema 白名单/maxDepth=0/minimal preset）；不经 task 记录（v1 无 taskId 阶段） |
| 原文载体 | T0.3 `timeline.append`（PIPE 单漏斗，`credential='user-original'`）；检索/复用走 T1.1 gate 既有路 |
| 目标创建 | T0.1 `goalTree.create`（domain v2 扩展字段 source/intakeProposalId，§3.4）；树不变量复用 |
| 审计回放 | draft/proposal 双写 `intake/change` → T0.7 `audit_index` 实体种类 +2；`replayCheck` sources 扩 intake 族；kill -9 冒烟增"澄清中/待批"场景 |
| KV-cache | 零父侧工具/schema 增量（无模型工具面），不影响 T0.4 前缀稳定性 |

## 6. 验收标准（对 Gate G4-① 的贡献项）

> **验收结果（2026-10-13 IT16，全部通过）**：①原文隔离=timeline user-original chunk 唯一载体+域内零全文（集成门实证）✓；②抽取可解释=ExtractionMeta 随记录落盘 ✓；③问题确定性=deriveQuestionsFromSeed 纯函数+轮次帽 escalation ✓；④校验门=四类坏提议确定性拒+留档 ✓；⑤确认门=whatToShow 摘要+token 一次性重放拒 ✓；⑥代建追溯=拓扑序+source='intake' 且 intakeProposalId 全链 ✓；⑦拒绝/supersede=已建目标不动 ✓；⑧半树显式终态=cancelled+部分回填 ✓；⑨审计=双写配对+回放零差异（双表按 payload 键形状分账）✓；⑩单活动草稿 fail-loud ✓。

1. **原文隔离**：长文本需求经 intake 后，主会话 surface 无原文（只存 timeline user-original chunk + 草稿结构化字段）；回放主会话 log 可证；
2. **抽取可解释**：草稿带 `ExtractionMeta`（provider/model/schemaHash/at）；同 schema 同输入的抽取单测确定性（scripted provider）；
3. **问题确定性**：`deriveQuestions` 同草稿同输出（纯函数单测）；澄清回答回写后 blocking 问题消减；轮次帽超限 escalation 呈现（禁静默）；
4. **分解校验门**：criteria 空 / tempId 悬空 / 预算非法 / 成环 / 多根的提议被确定性拒（`validation.passed=false` 禁提请）；过闸提议才可 `confirmRequest`；
5. **确认门**：审批请求 whatToShow 含目标树摘要 + 影响面（将创建 N 个目标/含约束）+ 定级理由；token 一次性（重放被拒）；无超时自动过；
6. **代建追溯**：commit 按拓扑序建树成功；每个 goal 节点 `source='intake'` ∧ `intakeProposalId` 非空（T0.1 v2 加载期断言）；`createdGoalIds` 回填；
7. **拒绝/取消**：rejected/cancelled 后禁建；草稿可被新草稿 supersede（链指针可溯），已建目标不动；
8. **半树显式终态**：commit 中途失败（第 k 个节点创建抛错）→ 已建节点保留 + proposal 落 `cancelled`+unfinished 清单，禁静默回滚；
9. **审计**：draft/proposal 变更 ↔ `intake/change` 逐一配对；`replayCheck` 覆盖 intake 族零违规；kill -9 于 clarifying/pending-approval 恢复后草稿态不丢、token 过期回 pending 可重签（T3.2 J4 语义）；
10. **单活动草稿**：第二个草稿 intake 时旧草稿未终态化被拒（fail-loud）。
